# RFC 9700 hardening — v0.5 slice 4

## Invalid-client rate limiting (RFC 9700 §4.2, local policy)

- Failed client authentication (`invalid_client`) is counted per claimed client id; successes are never counted. The claimed id comes from the Basic header, `client_id`, or the `client_assertion` `iss` (unverified, used only as a counter key). Unknown ids are counted too, so volume cannot be used to probe which ids exist.
- At `OAUTH2_CLIENT_AUTH_MAX_FAILURES` (default 10) failures inside a fixed window of `OAUTH2_CLIENT_AUTH_WINDOW_SECONDS` (default 300) every further attempt for that client, **including one with correct credentials**, gets `429 temporarily_unavailable` with `Retry-After`. The check runs before any credential work, and a store error fails closed (500).
- Applies to every endpoint that authenticates a client (token, revoke, introspect, device authorization, PAR).
- The window starts at the first failure and is not extended by later ones, so a steady attacker cannot lock a client out forever; it lifts by itself.

### Storage design

Two methods on the existing `Store` port, no new infrastructure: `rateLimitCount(key, now)` (read) and `rateLimitHit(key, windowSeconds, now)` (atomic increment, returns the new count). SQLite uses a single `INSERT … ON CONFLICT DO UPDATE … RETURNING` on a new `rate_limits` table (created with `CREATE TABLE IF NOT EXISTS`, no migration); PostgreSQL/MongoDB use the shared `DocumentStore` (`ratelimit` kind) inside the adapter transaction like `consumeDpopJti`. Because the database decides, the limit holds across processes and restarts. The key is `cauth:` + SHA-256(client id), so raw ids are not stored in the counter.

Alternatives considered:
- *In-process Map* — simplest, but per-process, resets on restart, and trivially bypassed behind a load balancer. Rejected (task requires store-backed).
- *Reuse `consumeDpopJti` with N slot keys* — no port change, but cannot be read without consuming, so a locked client could not be refused before credential checking. Rejected.
- *Per-IP limiting* — needs trusted-proxy address handling that this server does not have; left to the edge.

Trade-off: an attacker who knows a client id can deliberately lock that client out (availability DoS). That is inherent to per-client limiting; the window is bounded and per-IP limits belong at the edge.

### Conformance

The contract's rate-limit scenarios (`abuse.invalid-client-rate-limited`, `rate-limit-per-client`, `success-not-counted`) are draft placeholders at the pinned revision, deferred, and not coverage. They share one SUT with the stable scenarios and the draft one fires 100 failed auths, so `scripts/conformance-run.sh` sets `OAUTH2_CLIENT_AUTH_MAX_FAILURES=1000`. Limiter behaviour is covered by `test/rate-limit.test.ts` instead. `sender-constrained` is claimed in `conformance.yaml` and has its CI step (added with #17); all five profiles pass locally against the pin.

## Redirect / CSRF / replay review

Already enforced: exact `redirect_uri` matching (loopback port exception only), no redirect to unregistered URIs, PKCE S256 required on every authorization request, `iss` returned on authorization responses (mix-up, §4.4), `state` echoed, one-time authorization codes, refresh-token rotation with family revocation on replay, DPoP `jti` and `private_key_jwt`/jwt-bearer `jti` replay stores.

Added here: authorization redirects send `Referrer-Policy: no-referrer` and `Cache-Control: no-store` so codes in the `Location` URL do not leak through Referer headers or caches (§4.2.4/§4.12).

Not done (follow-up): revoking access/refresh tokens already issued from an authorization code when that code is replayed (RFC 6749 §4.1.2) — needs a code→token link in the Store.
